# Proposal: group-invitations

## Why

Today every invite link maps to exactly one guest: one `invites` row, one RSVP, one photo slot. The couple also wants **group links** — one shareable URL for a family, a group of friends, or a plus-N party — where each person who uses it gets their own independent RSVP and photo slot, capped by an admin-set quota. Without this, the couple must either mint individual invites for people they can't name in advance (plus-ones, kids) or accept that a shared link collapses everyone into one RSVP/photo identity that overwrites itself.

## What Changes

- **Parent-child invite model**: `invites` gains `parent_id` (nullable self-FK), `type` (`individual` | `group`, default `individual`), and `max_members` (nullable, set only on groups), guarded by CHECK constraints. Each group _member_ is a real child row in `invites`, so `rsvps` (PK `invite_id`) and `guest_photos` (unique `invite_id`) give per-member RSVP and per-member photo slots with **zero changes to those tables**. The baseline migration is regenerated with the new columns. The existing `packages/db/local.db` held preserved guest data (11 invitations / 5 RSVPs / 4 photos from the 2026-09-16 handoff); **the owner confirmed on 2026-09-28 that this data is disposable** and authorized the replacement procedure in `ops/README.md`, so the local DB is deleted and recreated from the regenerated baseline (design D5, option A) — no additive migration, no data-conversion step.
- **Slots are claimed on explicit action, not on link open**: opening `/{groupId}` only sets the cookie and bumps seen-metrics (unlimited browsing, link forwarding is free). A member claims a slot via a new `POST /api/invite/claim` endpoint with their `displayName`; the claim atomically mints a child invite under the quota and rebinds the `ww_invite_id` cookie to the child id. From then on RSVP, photo upload, greeting, and open-tracking work unchanged under the member identity.
- **Hard quota, race-proof**: the claim is a single atomic `INSERT … SELECT … WHERE count < max_members … RETURNING` statement, so simultaneous claims serialize in SQLite and member N+1 gets `409 group_full` instead of a slot. Storage failures (`SQLITE_BUSY` et al.) return `503`, never a false `group_full`. Visitors who arrive after the quota is exhausted can still browse; claim/RSVP/photo actions surface a "group is at capacity" state.
- **Sticky member identity with sliding expiry**: `GET /{groupId}` keeps a member cookie belonging to that group pointed at the member (re-set with the same value and a refreshed `Max-Age`) instead of rebinding to the group. A `GET /{groupId}?fresh=1` path explicitly rebinds to the group identity — the cookie-only "Not you? Claim your own spot" escape hatch for shared browsers; it creates no rows, consumes no slot, and does not delete the member row (so it does not free the slot either); only the group row's seen-metrics move. Because a state-changing GET is unreachable by any origin check and `SameSite=Lax` still sends the cookie cross-site, the release carries two gates of its own: a `Sec-Fetch` check (honoured only for `Sec-Fetch-Site: same-origin`/`none` with `Sec-Fetch-Dest: document`) and a capacity check (refused when the group has no open slot, or when its quota cannot be read — fail closed).
- **Group-aware endpoints**: `GET /api/invite/me` reports the identity kind (`individual` | `group` | `member`) plus group quota state for group cookies; `POST /api/rsvp` and `POST /api/guest-photos` with an unclaimed group cookie fail with `409 claim_required` instead of writing shared state.
- **Admin API**: `POST /api/admin/[token]/invites` accepts `type` + `maxMembers` (2–50); `GET` returns group entries with quota, claimed count, RSVP/photo counts, and a per-member breakdown.
- **App-level origin checks replace the framework's**: implementing the above surfaced a pre-existing production defect — Astro's `security.checkOrigin` compares `Origin` against `new URL(request.url).origin`, whose scheme comes from `req.socket.encrypted`, so behind the documented Caddy deployment (TLS terminated upstream) it can never match and **every form-like and bodiless POST 403s in production**. Guest photo upload and invite-open tracking were already dead this way; `/api/rsvp` survived only because JSON bodies are exempt, which is why nobody noticed. It cannot be fixed from config. Owner decision D1 (option A): `checkOrigin` is disabled and replaced by a proxy-aware `isSameOriginRequest()` (`src/lib/same-origin.ts`) on all four cookie-authenticated POSTs, answering `403 { "error": "cross_origin_post" }`, with `tests/origin-guard.spec.ts` failing the build if an endpoint drops the call, if the guard sits after a side effect, or if `checkOrigin` is re-enabled. `api/admin/[token]/invites` is exempt: its authority is a secret in the path, not an ambient cookie.
- **Doc sync**: `SPEC.md` and the ops docs are updated for the sticky-cookie exception, the new columns, the admin group contract, and the new 409 codes.

## Capabilities

### New Capabilities

- `group-invitations`: the group invite model and lifecycle — parent/child schema, atomic quota-guarded slot claiming via `POST /api/invite/claim`, sticky member cookie on link revisit with a `?fresh=1` release path, capacity-full behavior, and admin group creation/listing breakdown.

### Modified Capabilities

- `database-baseline`: the baseline `invites` table definition gains `parent_id`, `type`, `max_members`, the parent index, self-FK, and CHECK constraints (regenerated as one migration per the replace-as-one-unit convention).
- `invite-session`: `GET /api/invite/me` response shape extends beyond `{ displayName }` to carry identity kind and, for group cookies, quota/claimed state so clients know to run the claim flow. **Plus a new ADDED requirement**, "Cookie-authenticated mutations verify the request origin", covering the app-level guard, the `checkOrigin` prohibition, the proxy reconstruction, and the admin-token exemption.
- `rsvp-responses`: the "Submit RSVP via cookie identity" requirement is re-scoped — a group cookie (valid but unclaimed identity) is rejected with `409 claim_required`; claimed member invites satisfy the per-invite contract unchanged.
- `guest-photos`: the "One photo per invite" requirement gains a `409 claim_required` outcome for group cookies; per-member one-photo uniqueness falls out of the existing `invite_id` unique constraint.
- `rsvp-section`: the "Server-rendered invitee controls" requirement is gated on identity kind — group cookies get a claim prompt / capacity state instead of the confirm button, and claim success reloads the page so all SSR surfaces re-render under the member identity.
- `guest-photo-trail`: the "Posting eligibility comes only from resolved server state" requirement gains an identity-kind gate (unclaimed group identity ⇒ no chooser) and mandates error-code (not status-code) classification of `409` upload responses.

## Impact

- **DB (`packages/db`)**: `schema/invites.ts` gains `parentId` (self-FK), `type`, `maxMembers` + `invites_parent_id_idx` + four CHECK constraints; baseline migration `0000` regenerated as a unit (delete `src/migrations/**`, regenerate `--name initial`). `rsvps` and `guest_photos` schemas untouched. The guarded migrator refuses the changed baseline on existing DBs — operator replacement per `ops/README.md`.
- **Web (`apps/web`)**: new routes/modules `src/pages/api/invite/claim.ts`, `src/lib/group-claim.ts` (atomic claim helper, precise collision detection), `src/lib/invite-id.ts` (id generation + collision classifier), and `src/lib/same-origin.ts` (proxy-aware origin guard); `src/pages/[id].ts` (sticky member cookie, `?fresh=1` release, `type` in metrics/fallback queries); `src/lib/invite-session.ts` (`resolveInvite` surfaces invite kind/group state; shared `readGroupQuota()`, `inviteCookieOptions()`/`setInviteCookie()` as the single cookie-attribute source); `src/pages/api/invite/me.ts`, `src/pages/api/rsvp/index.ts`, `src/pages/api/guest-photos/index.ts`, `src/pages/api/invite/opened.ts` (group-cookie handling and the origin guard); `astro.config.mjs` (`security.checkOrigin: false`, with the rationale and the Astro Actions caveat inline); `src/pages/api/admin/[token]/invites.ts` (create groups, list breakdown); `src/pages/index.astro` + `src/components/RsvpSection.astro` (SSR `kind`/quota plumbing, claim prompt, capacity state, and the "Not you?" release rendered as a `<button>` with a two-step dwell guard rather than an anchor — a static `href` is bypassed by middle-click, the context menu, iOS long-press, drag, and copy-link); `src/scripts/photo-trail.ts` (narrow the 409 success branch to `already_posted`, claim/capacity states, new `PHOTO_ERRORS` entries).
- **APIs**: additive response fields on `GET /api/invite/me` and admin list; new `POST /api/invite/claim`; new `409` outcomes on RSVP/photo POST for group cookies. No endpoint removals.
- **Docs**: `SPEC.md` (sticky-cookie exception, columns, admin contract, 409 codes), `README.md` + `NOTE.md` (rebind rule gets the sticky exception; claim endpoint), `ops/README.md`, `ops/MODERATION.md` (self-FK deletion constraint).
- **Tests**: `tests/origin-guard.spec.ts` ships with this change (owner-requested architecture guard; mutation-verified). Deferred to the testing pass: new Playwright specs for claim lifecycle, concurrent-claim quota enforcement, member isolation (RSVP/photo), sticky-cookie revisit, capacity-full UX, and admin group breakdown; baseline schema assertions and the `/api/invite/me` exact-shape assertion updated for the new columns/fields.
- **Risk**: the atomic-claim statement is the only quota guard — it must stay a single statement (not read-then-write) and is covered by a dedicated concurrency test. Cookie-based identity means one person can claim multiple slots from multiple browsers; the quota bounds the blast radius and the admin breakdown makes double-claims visible.

Two residual risks are accepted by owner decision and filed as follow-up changes rather than solved here. (1) A claim that commits and then loses its response — process death or a connection reset mid-statement — leaves the guest's browser without the new cookie, so their retry mints a second member row; the handler-survivable case is reconciled by `findCommittedClaim`, the crash case cannot be. The client's ambiguous-outcome copy (any 5xx, plus a thrown fetch) steers guests away from a blind retry; behind Caddy that failure arrives as a proxy-synthesised 502/504, not an app 503, so the copy keys on `>= 500`. Filed as `member-slot-release`. (2) A GET release enters browser history and replays with `Sec-Fetch-Site: none`, which the gate must allow; the capacity gate makes the replay inert only once the group is full. Filed as `release-via-post`.
