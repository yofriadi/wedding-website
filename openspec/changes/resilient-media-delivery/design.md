Google's page is not light — its markup references 217 MB of video variants across 26 autoplay elements, and at the five-second mark only one of 32 media elements was advancing. It has no empty state because nothing visible is ever detached from a source: every `<img>` carries a real `src`, every box has intrinsic dimensions, and no text sits behind a JS-gated opacity.

**Correction to an earlier reading of the last table row.** The 9/9 figure was measured with JavaScript _enabled_, at rest, at the top of a 19 006 px document. All nine `[data-scroll-fade]` participants sit far below the fold (`index.astro:220`, `EventTimes.astro:38/51`, `RsvpSection.astro:93/176/195/241/249`, plus `#venue-map`), so opacity ~0 is the reveal's _intended_ pre-state, not a defect. The visibility floor this change wants **already exists for reveals**. It does not exist for overlays — see D5.

Three constraints shape this design and are not negotiable:

1. **Private media.** `apps/web/public/` holds 53 tracked files, 27 of them currently `skip-worktree`. The repository ships placeholders at those paths; `tools/restore-private-media.sh` overlays the real photos from gitignored `originals/private-media/` and hides them from git. `/originals/` and `apps/web/public/*.mp3` are gitignored. **Any generated variant of a real photo is itself private media** and must never be committed.
2. **The tier probe depends on the cache policy.** `Layout.astro` documents that the warm-cache locality inference requires everything under `public/` to be served `max-age=0` + ETag, so a returning guest produces ~23 conditional GETs whose 304s are the signal. Switching `public/` to `immutable` would make those entries indistinguishable from blocked resource timing and would silently stop the inference firing, **with no test failing**. `Caddyfile.example` sets no cache headers, so the Astro/node default is what ships.
3. **`media-tiering` now has an archived base spec.** `adaptive-media-tiering` was archived on 2026-09-22 with all 63 tasks closed, so `openspec/specs/media-tiering/spec.md` exists and this change's MODIFIED delta has a real merge target. The delta was re-diffed clause-by-clause against the archived base after the move: all six base clauses and all five base scenarios are preserved, with two scenarios added intentionally. The earlier hazard — an agent-driven `openspec-sync-specs` MODIFIED branch with no base spec to merge into, which could have silently dropped the amendment — no longer applies **in this working tree**.

   **Correction found in review, and it is load-bearing.** `openspec/specs/media-tiering/spec.md` is **untracked** (`git ls-files` returns nothing for it), as are `families-section/` and `story-teaser/`. The archive commit `5b3088d` moves the delta to `archive/2026-09-22-adaptive-media-tiering/specs/media-tiering/spec.md` and creates nothing under `openspec/specs/`, so the base spec on disk is hand-written and uncommitted. On a fresh clone, in CI, or for any other contributor the MODIFIED delta has **no merge target**, and `openspec archive resilient-media-delivery` would either fail or silently drop the amendment — precisely the hazard this constraint declares closed. `openspec validate --strict` passes only because the untracked file happens to be present here. Committing those three base specs is a prerequisite for archiving this change and is deliberately **not** done here: they are not this change's output, and two of them are being edited by other in-flight work.

Already present and usable: `sharp@^0.35.4` in `apps/web/package.json`; a hero variant convention (`wedding_photo-{390,640,1024,1536}.{avif,webp}`); an established blurred-placeholder pattern (`wedding_photo_blur.{avif,webp}`, 18 KB); and a `<picture>` promotion machinery in `ZoomParallax.astro` that already handles `<source>`-before-`<img>` ordering.

## Goals / Non-Goals

**Goals:**

- Zero image elements without a fetchable source, on every tier, with and without JavaScript.
- Device-matched bytes: a 390 px phone never downloads a 2048 px master.
- No content whose visibility depends on a script having run.
- Font payload and hint discipline that let first text and the LCP image start before the body finishes parsing.
- Achieve all of the above without weakening the tier probe, without committing private media, and without touching the verdict logic.

**Non-Goals:**

- Changing tier _detection_ — the 220 KB/s floor, the one-way ratchet, `net-tier:change`, the burst window, and the locality inference all stand.
- Changing `public/` cache headers or `Caddyfile.example`. Deferred to a follow-up (see Open Questions).
- Video and soundtrack strategy. `lamaran.mp4` (697 KB) and the 3.1 MB mp3 keep their current tier behavior.
- Replacing the bespoke collage promotion observer with native `loading="lazy"` on the collage. The observer stays because the tier still decides _which candidate_ loads.
- Any visual redesign. Placeholder fidelity is a delivery concern, not an art direction one.

## Decisions

### D1 — Variants are generated by a `sharp` script into a gitignored directory

A committed script (`apps/web/scripts/generate-media-variants.mjs`) reads masters from `apps/web/public/`, writes `apps/web/public/generated/`, and is wired as `prebuild` plus a `media:variants` script for dev. `apps/web/public/generated/` is added to `.gitignore`. Its input set is the **explicit list of base names the markup references** — the same list `resolveMasters()` requires both masters for, and `guardMarkupCoverage()` reads the markup back against — rather than a directory scan. Subdirectory scanning was considered and dropped: `public/map/` is the only raster subdirectory and its sole consumer is `venue-map.ts:123`'s `bannerHtml()`, which the server-rendered-markup scoping defers to task 7.4. Scanning it would emit **16** files nothing consumes (3 bases × 2 formats × (2+2+1) rungs, plus 3 placeholders per format), and D3 names dead output as the criterion for rejecting an alternative — so the relative-path machinery goes too, and comes back with 7.4 if that follow-up lands.

The input set is explicitly bounded, because `apps/web/public/` also holds `lamaran.mp4`, the 3.1 MB `.mp3`, `favicon.svg`, and the `wedding_photo_blur` pair. Non-raster files, anything already under `generated/`, and the blur layers **cannot enter the input set at all** — the script iterates an explicit whitelist and never enumerates `public/`, so there is nothing to skip (the `responsive-media` requirement states this correctly; this paragraph previously described a scan the script does not do). The `wedding_photo*` hero family is the one exclusion that is genuinely enforced **by name**, in two places: `guardInputSet()` hard-errors if a listed base matches the prefix, and `guardMarkupCoverage()` filters the same prefix out of the names it reads back from `markup` — a load-bearing filter, since `hero-media.ts` yields two such names — `wedding_photo-1024` from `HERO_FALLBACK_SRC` and `wedding_photo_blur` — both present in `public/` and neither in `BASES`, so removing the filter throws. Its two `HERO_SRCSET_*` literals contribute nothing, because a comma-separated candidate list inside one quoted string is a **fourth reference shape** the patterns do not recognise: a live instance, in the exact file the explicit floor exists to cover, of the blind spot the risk register below names. The prefix covers the eight pre-existing `wedding_photo-{390,640,1024,1536}` derivatives plus the two masters. A `-w<digits>` suffix rule is _not_ sufficient and was the original wording: those files carry `-390`/`-640`/`-1024`/`-1536`, which it does not match, so the generator would emit exactly the variants-of-variants (`wedding_photo-390-w390.avif`) the rule exists to prevent.

Generation SHALL NOT upscale. Several masters are narrower than the configured widths — `square-mid-left` 473 px, `event-resepsi` 584, `awal-perkenalan` 591, `portrait-bottom-left` and `event-akad` 768 — so the script emits only widths at or below the master's intrinsic width, and markup derives its candidate list from the same rule (both know the declared `width`). Otherwise the spec's "variants at every configured width" would mandate detail-free upscales, and at 390 CSS px @2x the browser would pick a **1280w upscale** for `event-resepsi` and `awal-perkenalan`, working against task 5.9's ceiling.

**The master is always the top candidate of its derived set, declared at its intrinsic width.** This is the repository's existing idiom — `HeroZoom.astro:7` carries `/wedding_photo.avif 768w` between the `-640` and `-1024` derivatives — and it is load-bearing here rather than cosmetic. Without it the no-upscale rule leaves `square-mid-left`, `event-resepsi` and `awal-perkenalan` with exactly one generated candidate (`-w390`), which violates `responsive-media`'s two-resolution requirement, makes task 5.6's "multi-candidate `srcset`" impossible for `EventTimes`, and silently _regresses_ `event-resepsi`: it ships its 584 px master today into a full-bleed `w-full` card, and would afterwards offer 390 px as its widest candidate.

Generation must also be visible to Turborepo. `turbo.json` declares `build.outputs: ["dist/**", ".astro/**"]` with `$TURBO_DEFAULT$` inputs, and a gitignored `generated/` is in neither. **The entry must be `public/generated/**`, not `apps/web/public/generated/**`: Turborepo resolves `outputs` relative to the package**, which is why the existing `["dist/**", ".astro/**"]` mean `apps/web/dist` and `apps/web/.astro` — there is no root `dist/`, and `.gitignore:7` ignores `dist` globally. A root-relative glob would silently match nothing and cache nothing.

The rationale matters, because an earlier version of it was wrong. Astro copies `public/` into `dist/client/`, so `dist/client/generated/**` is already inside the cached `dist/**` and _cannot_ be missing from a restored `dist/` — a deployed artifact is safe either way. What the glob actually restores is the **working tree** `apps/web/public/generated/`, and that matters for two paths: `astro dev` after a cached `build` (dev serves from `public/`, not `dist/`), and the generator's own mtime comparison, which would otherwise see no outputs and redo work — or worse, see stale ones. The alternative, generation as its own task that `build` `dependsOn`, is unaffected by the resolution rule and remains valid.

Because generation reads whatever master is _present_, the same script produces placeholder-derived variants in CI and real-derived variants on the machine that ran `restore-private-media.sh`. Nothing private is ever staged, and no `skip-worktree` bookkeeping extends to generated files.

_Alternatives considered._ **`astro:assets` / `<Image>`**: rejected — it requires masters under `src/`, which would move private media out from under the overlay script's paths and its `skip-worktree` handling, and the Astro sharp service would emit derived real photos into `dist/client/_astro/` with hashed names that are awkward to keep out of git during local builds. **Request-time resizing**: rejected — this is an SSR node standalone deployment with no image CDN, so per-request `sharp` work would land on the guest's TTFB, which is already 4.5 s on a throttled link. **Committing variants**: rejected outright by constraint 1.

### D2 — Deterministic naming; the only manifest is a build fingerprint, not a render-time index

Candidates are named `<base>-w<width>.<ext>` for widths 390, 768, 1280, and placeholders `<base>-lqip.<ext>`. Markup derives candidate URLs from the master filename by string convention, and always appends the master itself as the top candidate at its intrinsic width (see D1).

A JSON manifest was considered and rejected: the site is `output: "server"`, so components render per request, and a manifest would couple render time to a build artifact that may not exist yet on a fresh clone. Deterministic names let markup be correct before generation has run.

That leaves a real hole: a base name present in markup but absent from `public/` yields a guest-facing 404, and there is no build-time HTML to scan for it under `output: "server"`. The repository already has the right idiom — `WelcomeGate.astro:19-28`'s `gateBgAssetExists()` (called at `:30`) does a render-time `existsSync` against `../../public${src}` and `../../client${src}`. Generation additionally checks its output against the explicit list of base names the markup references — the same list that now bounds its input set — so a missing master fails the build rather than the guest's page.

The hero's existing `wedding_photo-{390,640,1024,1536}` files are left where they are and referenced directly; they predate this convention and moving them would churn the tier probe's asset set for no gain.

### D3 — Placeholders are tiny external files, not inline data URIs

Each master gets an LQIP at ~32 px wide, blurred, budgeted at ≤ 4 KB, with the generation step failing when one exceeds it. Ten collage placeholders therefore cost ≤ 40 KB on a lite tier — the price of never showing an empty frame.

The placeholder is delivered through the existing `<picture>` as a live AVIF `<source>` plus a WebP `<img src>` pair, mirroring how the collage already carries one AVIF `<source data-srcset>` and one WebP `<img data-src>` (`ZoomParallax.astro:128-138`). Both formats are therefore wired; generating an AVIF twin that no markup references would be dead output.

**The exception this principle has, stated rather than left to be discovered.** `generateFor()` emits a placeholder pair for **every** listed base, and `placeholderSrc()` has exactly one caller — `ZoomParallax.astro`. So the five non-collage bases (`awal-perkenalan`, `keluarga-yofri`, `keluarga-acik`, `event-akad`, `event-resepsi`) each get an AVIF and a WebP placeholder nothing consumes: **10 files, 2 452 B on disk, zero guest bytes**. That is dead output of exactly the class D3 rejects a 16-file alternative for, and `pruneStale()` will never retire it because `expected` seeds an LQIP per base unconditionally.

It is recorded rather than coded away. Whether a base has a placeholder consumer is not decidable from source text — `ZoomParallax` calls `placeholderSrc(base, …)` on a variable ranging over a config array — so guarding it would mean a fourth regex heuristic of the kind `MARKUP_BASE_PATTERNS`' own comment warns against, or a third hand-maintained list (`PLACEHOLDER_BASES`) of the kind `guardMarkupCoverage()` exists to police. Neither is worth 2.4 KB. The generator also cannot know which bases a _future_ component will placeholder, and follow-up §2 (`bannerHtml()`) is precisely such a change. `spec.md:63` now scopes its "no file nothing consumes" clause to resolution variants and points here.

Inline `data:` URIs were considered and rejected. They would remove ten requests, but production sits behind Caddy over HTTP/2 where ten multiplexed tiny files cost roughly one RTT, and inlining would inflate an already 135 KB HTML document, defeat caching of the placeholder across navigations, and break the existing `<picture>` promotion machinery that swaps `src`/`srcset` attributes.

**The ten requests are paid on the `full` tier too, and that is now measured rather than assumed.** A `full`-tier guest promotes during the parse via the inline promoter, but Chromium's preload scanner runs ahead of the parser and queues the live placeholder `srcset` before that script mutates the DOM. Observed at 390 @2x on a scrolled full-tier pageview: **23 `/generated/` requests — 10 discarded LQIPs, the 10 promoted collage candidates, and the 3 lazy `TimelineScroll` images** — against **13** on the no-script leg, which makes the same 10 LQIPs and the same 3 timeline images with nothing promoted. The legs differ by exactly the 10 promotions. (An earlier version of this paragraph read "20 against 13", setting a collage-only subtotal beside a total; the pair did not close.) The waste is 3.27 KB, and the requests are multiplexed, so the trade above still holds; it is recorded here because D3 weighed inlining partly on "they would remove ten requests" and that saving is not available to the tier that could most afford it.

The existing 18 KB `wedding_photo_blur` is too large to generalise as a per-image placeholder; it stays as the hero's blur-up layer.

### D4 — Promotion becomes a candidate swap, not a source addition

`ZoomParallax.astro`'s `promoteImage` and the inline promoter in `pages/index.astro` keep their `<source>`-before-`<img>` ordering (setting the `<img>` `src` first makes the `<picture>` re-resolve and would fetch WebP then AVIF over it). Everything else about the precondition changes.

**There is a second presence-keyed guard, on the `<source>` side, with the identical defect.** `promoteImage` selects `source[data-srcset]:not([srcset])` at `ZoomParallax.astro:229`, and the inline copy does the same at `index.astro:190`. D3 and task 5.1 make the AVIF `<source>` carry a **live** LQIP `srcset` while keeping the full-resolution set in `data-srcset` — after which `:not([srcset])` never matches, the `<source>` is never promoted, and because `<picture>` resolves to the first matching `<source>` (the AVIF one, and D4 preserves that ordering) **every AVIF-capable engine keeps the 32 px placeholder forever**. That is strictly worse than the `<img>`-side failure above, and invisible to the whole verification set: `data-promoted` is still set, task 5.7's repointed probe still reads 10, and task 6.2's "zero `<img>` without a fetchable source" still passes.

So both selectors change, in both copies: `img[data-src]:not([src])` (`ZoomParallax.astro:185`) becomes **`#zoom-parallax-container img[data-src]:not([data-promoted])`**, and `source[data-srcset]:not([srcset])` becomes **`source[data-srcset]`** — the `:not(…)` clause is redundant once promotion is gated by the `<img>`'s marker. Promotion overwrites both `src` and `srcset`, and sets `data-promoted` afterwards as the sole idempotency mechanism, which is what the amended `media-tiering` requirement specifies. The "downgrade does not un-promote" guarantee carries over unchanged.

The existing `data-src`/`data-srcset` attribute names are **kept**, not renamed. The `media-tiering` delta is the normative artifact and specifies them; task 5.1 ships markup using them. Introducing a new `data-hires` name in the selector only — as an earlier draft did — leaves `querySelectorAll` matching nothing, so no image ever promotes. That is the same silent-failure class twice over: on the `<img>` side the selector matched but the write was suppressed; on the `<source>` side the write was fine but nothing was selected. In both cases `[src]`/`[srcset]` stopped being a discriminator the moment every element gained one, and only the marker survives as one.

### D5 — The reveal floor already exists; the overlay floor does not

`scroll-fade.ts` needs no behavioral change. Delivered markup and initial computed style are already opacity 1 (nothing in `src/` sets the attribute below 1 outside the reduced-motion block), and `initScrollFade` never writes opacity except in that branch — the opacity-0 writes come from `onScroll()`'s measured pass, which already darkens only what it has measured as outside the reveal window. That is precisely what `progressive-enhancement` requires. This phase therefore **codifies an existing invariant** rather than introducing one: a comment recording it, and — via task 3.6, **deferred to the testing pass and not yet written** — a no-script case that would fail if a future rule ever set the attribute below 1 in delivered CSS. Until 3.6 lands the floor is documented and unguarded; an earlier draft of this sentence said "codifies and regression-tests", which claimed 3.6's deliverable from 3.3's checkbox. The nine measured participants come from `index.astro:220`, `EventTimes.astro:38` and `:51` (the latter rendering **twice**, so the citations yield ten DOM elements for nine measured — `event-times.spec.ts` asserts `toHaveCount(2)`), `RsvpSection.astro:93/176/195/241/249`, and `VenueMap.astro:137`.

The genuine gap is overlays. `index.astro:133` ships `<div id="loading-screen" class="fixed inset-0 z-50 …">` with an opaque `background-color: var(--loading-bg)` (`:485`), dismissed only by JS (`doHideLoadingScreen` → `loader.remove()`, `:395`). `noscript` appears in `WelcomeGate.astro`, `ZoomParallax.astro`, and `VenueMap.astro` — **not** in `index.astro`. So a no-script guest is left behind an opaque full-viewport layer, and `tests/families-reveal.spec.ts` already acknowledges it in a comment ("the SSR'd loader/gate overlays also never dismiss without JS"). The fix mirrors the in-repo idiom: `<noscript><style>#loading-screen{display:none}</style></noscript>` plus the `@media (scripting: none)` twin `WelcomeGate` uses.

**The no-flash argument, corrected.** It is _not_ true that everything in the viewport computes to opacity 1. With `enterThreshold = min(vh * 0.32, isCard ? 240 : 160)` (`scroll-fade.ts:39-45`), an element inside the bottom 160 px band (240 px for `data-scroll-fade="card"`) is partially entered: at `vh` 844 and `rect.top` 800, `enterProgress` is 0.275, eased to ≈ 0.185, while `exitProgress` is 1 — so opacity ≈ 0.19. The no-flash claim holds only because no current participant sits near the initial viewport, i.e. it passes **vacuously**. The invariant is therefore stated the way the code actually behaves: elements with `rect.top <= vh - enterThreshold` (`enterProgress === 1`, fully entered) stay at 1; partially entered bottom-band elements are exempt. Any future participant placed near the fold must respect that boundary.

_Alternatives considered._ **An inline head script that pre-applies the hidden state**: rejected — it reintroduces JS-gated invisibility and adds parse-blocking work. **A CSS `:not(.js)` class toggled by an inline script**: rejected for the same reason, and it would flash in the opposite direction. Both were aimed at a problem the reveals do not have; the overlay fix needs neither, because `<noscript>` and `@media (scripting: none)` are declarative.

### D6 — Fraunces moves from `full` to `standard`, keeping optical size

Switch `@fontsource-variable/fraunces/full.css` + `full-italic.css` to `standard.css` + `standard-italic.css`. Measured latin-subset costs:

| entrypoint              | axes                   | latin normal | latin italic | total    |
| ----------------------- | ---------------------- | ------------ | ------------ | -------- |
| `full` (current)        | wght, opsz, SOFT, WONK | 118.2 KB     | 146.2 KB     | 264.4 KB |
| `standard` (**chosen**) | wght, opsz             | 65.7 KB      | 79.6 KB      | 145.3 KB |
| `wght`                  | wght only              | 35.8 KB      | 44.6 KB      | 80.4 KB  |

`wght` is 65 KB cheaper but pins the optical-size axis at its default. Fraunces is used for display text up to `clamp(2.5rem, 11.5vw, 7.5rem)` in `HeroZoom`, where `font-optical-sizing: auto` drives real contrast and spacing differences. SOFT and WONK have no consumer anywhere in `src/`. The 65 KB is spent on an axis that is visually load-bearing.

`@fontsource/geist-sans` (400/500/600/700) is dropped entirely. `--font-sans` resolves `"Geist Variable"` first and the variable font covers weights 100–900, so the static family is unreachable; the measured load fetched none of its files. It still costs 15 `@font-face` rules and ~294 KB of build output including four legacy `.woff` files. The `"Geist"` entry in the token stack becomes dead and is removed with it.

Italic is retained on both families: `HeroZoom.astro:58` renders the display ampersand italic and `RsvpSection.astro:252` renders `font-serif italic`.

Vietnamese and Cyrillic subsets transfer no bytes — the site renders Indonesian and English. Note the mechanism: stock `@fontsource` entrypoints emit a `unicode-range`-gated `@font-face` for **every** subset they cover (`standard.css` emits three, `@fontsource-variable/geist/wght.css` emits five), so the declarations still ship; the range gate is what prevents the requests. The spec is written against the request list accordingly, not against emitted CSS — read literally, "shall not ship" would invite hand-written `@font-face` blocks, which is wasted scope. `latin-ext` is kept as cheap insurance for accented guest names (16.1 KB for Geist, fetched only when a range matches).

### D7 — Hints are minimal and cannot touch the cache policy

Add `preconnect` for the basemap tile origin (`{a-d}.basemaps.cartocdn.com`, per `venue-map.ts:518,523`), and `preload` for the latin serif `woff2` and the hero candidate. Two corrections to the obvious version of this:

- **`fetchpriority="high"` is already on the hero** (`HeroZoom.astro:17`), alongside `srcset`, `sizes`, `width`/`height`, `loading="eager"` and `decoding="async"`. **It is also on `WelcomeGate.astro:49`**, so two images carry it in markup; the `responsive-media` scenario "exactly one image carries `fetchpriority=\"high\"`" passes today only because `public/gate/gate-bg.avif` is absent and `hasGateBg` is false. Task 5.6 edits that exact `<img>` and must drop the attribute there, or the requirement breaks the moment the couple supplies the asset.
- **The hero preload needs `imagesrcset`/`imagesizes`.** A bare `<link rel="preload" as="image" href=…>` cannot express a `srcset` selection or negotiate format, so it would fetch a file the `<picture>` then discards — a double fetch on a throttled link, the opposite of the goal. It must mirror the `<img>`'s `srcset`/`sizes` and name the format the browser picks (AVIF). And because `sizes="min(280vw, 1536px)"` resolves to 1092 px at a 390 CSS px viewport, DPR 2 selects the **1536w** candidate, not `-390`; the hint targets what `sizes` actually chooses.

The font preload must reference the bundled, content-hashed URL — resolved via a Vite import in the Layout frontmatter (`import latinSerif from "@fontsource-variable/fraunces/files/fraunces-latin-standard-normal.woff2"`), not a literal package path, which 404s. Everything below the fold gets `loading="lazy"` except the collage, which stays on the tier observer per D4.

No `Cache-Control` or `immutable` change anywhere. Adding long-lived caching to `public/` would break constraint 2 silently.

## Risks / Trade-offs

- **A fresh clone has no `generated/` directory** → markup would reference 404ing candidates. Mitigations, all three needed: `prebuild` runs generation unconditionally and the script is idempotent; **`public/generated/**`** (package-relative — see D1) is added to `turbo.json`'s `build.outputs`, which restores the _working tree_ copy on a cache hit rather than the `dist/` copy Astro already caches inside `dist/**`; and the dev path is a documented `pnpm media:variants` before `pnpm dev` (a `postinstall` hook was considered and dropped — `astro dev` runs no `prebuild`, and a hook that silently regenerates on every install is worse than one explicit command). `prebuild` is honoured: root `build` is `turbo run build`, `apps/web` `build` is `astro build`, and pnpm 12 defaults `enablePrePostScripts` to true with no override in `pnpm-workspace.yaml` or `.npmrc`. Task 4.6's cache-hit check must therefore inspect the **working tree**, not `dist/`. The guest-facing 404 case is caught by the generator's completeness checks, not by scanning build output — **within a stated scope**: the checks read an explicit floor of four sources unioned with everything `discoverMarkupSources()` finds by walking `src/` for the `media-candidates` import — and the union matters in the direction the floor provides, not the one its name suggests: `src/lib/hero-media.ts` contains **zero** occurrences of that import (it is a module of plain URL literals), so discovery never finds it and it is scanned only because the floor lists it by hand. Any new module of that shape must be added the same way and recognise three reference shapes, so a fourth syntax a future contributor invents is not detected. Closing that properly needs AST parsing, judged disproportionate; `baseOf()` is instead shared from `src/lib/media-candidates.ts` and applied _inside_ `variantSrcset`/`placeholderSrc`, so the one concrete divergence review found — a `baseOf` that stripped the leading slash but not the extension, which would emit `/generated/event-akad.webp-w390.avif` — is unreachable by construction rather than guarded. Two directions, both hard failures: `resolveMasters()` rejects a listed base with no master **or with only one format** (markup emits a `<source>` for both, so a single-format master leaves the other naming files that do not exist — worst on the `<img>` fallback path, which is reached precisely by engines that cannot do AVIF) and rejects a base whose two masters disagree on intrinsic width (one ladder is emitted for both, so a divergence would ship a file named `-w768` holding fewer pixels than the `768w` descriptor it is served under). `guardMarkupCoverage()` covers the inverse and more likely drift, since the list is hand-duplicated from three components: markup references a base that has a master in `public/` but is absent from the list. Without it nothing fails — generation skips the base, `variantSrcset()` still emits `/generated/<base>-w390.avif` from the naming convention alone, and every promoted image in that slot 404s. A reference whose master is absent does _not_ fail, so the cross-check cannot turn an unrelated source string into a spurious build failure.

  Scanning build output was considered and rejected: under `output: "server"` there is no build-time HTML, and while `dist/server/entry.mjs` does embed a `public/` inventory, that is a _disk_ listing rather than a reference list, so it cannot distinguish a consumed asset from an orphan. The render-time `existsSync` idiom survives only in `WelcomeGate` and `VenueMap`, whose assets are optional by design; the 15 generated bases are unconditional and are guarded at build time instead.
