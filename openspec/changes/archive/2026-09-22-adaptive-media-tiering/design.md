## Context

The homepage spends ~4.8 MB of media on every visit: ~1 MB of collage AVIFs (ZoomParallax), a 714 KB timeline video, and a 3.1 MB soundtrack — against ~70 KB of total page JavaScript. The previous change (`loader-timeline-photo-gate`) made the loading screen wait for the collage so the first scroll never lands on unfinished media; on Good-3G-class links that pushed the loader to its 16 s ceiling and the gate failsafe to 25 s, trading a broken first scroll for a ten-second phrase loop. Two audits also found spend nobody chose: the video's `autoplay` attribute defeats its `preload="none"` (714 KB races the parse on every network), and the soundtrack's `preload="auto"` buffers 3.1 MB before the guest hears a note.

Constraints: guests are mobile-first on unpredictable Indonesian cellular links; Safari/iOS lacks the Network Information API; the site is a single Astro bundle with no client router; the welcome gate's commit gesture is the only reliable audio unlock; no-JS guests must keep a readable page (the gate already hides itself via `<noscript>`).

## Goals / Non-Goals

**Goals:**

- Slow links get a lite variant that skips the expensive operations (eager collage, parallax binding, video fetch, soundtrack) instead of making everyone wait for them.
- Fast links keep today's full experience with parse-time collage fetches and the loader gate reduced to first-view media.
- One bundle, one component tree: the tier is a runtime attribute, not a second build or duplicated components.
- Detection that works on Safari: measured throughput, not API presence alone.

**Non-Goals:**

- Server-rendered variants or CDN-level image resizing (no server-side network signal exists; Save-Data headers are too rare to carry the design).
- Smaller collage renditions for lite (deferral alone removes the eagerness; generating a second rendition set is a separate photo-pipeline change).
- Flattening the timeline scroll-scrub story on lite: it is the wedding narrative, its assets are small, and its JS is already in the bundle via TimelineScroll.
- Upgrading a tier mid-session.

## Decisions

**D1 — Verdict ladder: synchronous API, then measured burst, then failsafe.** An inline head script sets `data-tier` before body parse from `navigator.connection` (saveData → lite; effectiveType slow-2g/2g/3g → lite; downlink < 1.2 → lite; else full). Engines without the API get `pending`. Alternatives rejected: server-side variant selection (no request header carries link quality; Client-Hints cover device, not network), and pure measurement (delays full-tier promotion past parse for everyone, including the 90%-Android majority that has the API).

**D2 — Measure the aggregate initial burst, payload bytes only.** A single small asset is a noisy probe (one RTT dominates a 20 KB hero candidate), so the probe is the burst the page downloads anyway: cumulative `transferSize` over the span from earliest `startTime` to latest `responseEnd`, i.e. the parallel link throughput the page actually experiences. Verdict below 220 KB/s (Good-3G sits ~180–190 KB/s; 4G/LTE sits an order of magnitude above) once ≥48 KB have transferred; a window-`load` fallback judges at ≥8 KB; a 7 s failsafe resolves `pending` to `lite`. Thresholds are tunables, pinned in the spec as behavior classes rather than constants.

What sits in the burst differs by path, and the asymmetry is load-bearing rather than incidental. On `pending` the soundtrack is not yet enabled, so the burst is hero + webfonts + the timeline's real sources (~100–400 KB) — a clean probe, which matters because `pending` is the only path where the verdict can _upgrade_, so a downward bias there would cost a fast guest the entire experience. On an API-`full` verdict the parse-time promoter (ten AVIFs, ~1 MB) and `enableSoundtrack()` (3.1 MB) are both in flight, so the burst is ~4.5 MB and dominated by the soundtrack — the very asset whose affordability is being decided. That reads circular but is conservative: a resource entry appears only when the resource _completes_, and the mp3 completes last, so at the first ≥48 KB judgment it has contributed zero bytes and only bandwidth contention, which biases the reading toward `lite` — free on a path where the verdict can only ever downgrade.

Two classes of entry are excluded from the count, both because they measure round-trip latency rather than throughput. Programmatic requests (`fetch`/XHR/beacon): this page issues same-origin API calls from a module script, and on a warm cache those can be the only non-zero entries left. And any entry that moved no body (`encodedBodySize === 0`): memory-cache hits report zero across the board, and 304 revalidations carry ~300 B of headers with no body — which matters here because everything under `public/` is served `max-age=0` + ETag, so a returning guest revalidates ~23 assets. `encodedBodySize` is never used as the byte count either; it would let a warm-cache hit measure disk speed and claim a fast link.

**Resolved: a payload-free burst with locality evidence resolves `pending → full`.** Excluding payload-free entries means a warm cache produces _no throughput verdict at all_, which left a returning guest on an engine without the Network Information API — Safari and Firefox, i.e. the whole iOS population — resolving to `lite` via the 7 s failsafe on every visit after the first, losing the tunnel zoom and the soundtrack on a fast connection with every byte of media already on the device. The original justification ("harmless — deferred media serves from cache instantly there") was self-refuting: if the deferred media is free to fetch, promoting it eagerly is equally free. So at `load`, an unresolved `pending` tier with at least five asset bodies that arrived without a payload transfer resolves to `full`. The evidence is not cache _timings_ — it is the fact that the bodies are local, which makes the fast/slow question moot for the media being deferred.

Two properties make this safe rather than optimistic. It **fails closed**: engines without Resource Timing sizes (Safari < 16.4) report `undefined` rather than zero, so nothing is counted, no evidence accumulates, and the failsafe still resolves `lite` — the pre-existing behavior, so the rule cannot do worse than the status quo on any engine. And it **never outranks a measurement**: the branch runs only when `judge()` reached no verdict, so a warm cache carrying a genuinely slow payload still resolves `lite` on the measurement.

The accepted risk is narrower and more common than "cache eviction". The revalidations prove the _probe set_ is local — hero, fonts, timeline photos, chunks. They say nothing about the collage or the soundtrack, which are never requested before promotion; the soundtrack in particular is fetched only on a `full` first visit. So the real case is a guest whose first visit resolved to `lite`, who reopens the link — the normal case on event day, on venue cellular — and now eagerly pulls 3.1 MB on an unmeasured link. Bounded: it is a background fetch, the loader gates on the hero alone, nothing breaks, and the next visit revalidates everything so it does not repeat. iOS Low Data Mode is the same case, since Safari never exposes it to the Network Information API — and never did on the first visit either.

A second mechanism reaches the same branch from a population the paragraph above does not name: **document TTFB**. `index.astro` awaits up to three Postgres queries before the head flushes and the response is `no-store`, while the burst window is measured from navigation start — so a document slower than 2.5 s pushes _every_ subresource `startTime` past it, erasing throughput evidence for **cold** entries as well as warm ones. A partially evicted probe set on a genuinely slow link, which would otherwise transfer ≥8 KB and be judged `lite` with the measurement outranking locality, instead presents `bytes ≈ 0` and resolves `full`. The new slice is narrow — partial eviction, TTFB over 2.5 s, under 8 KB of cold remainder, and a slow link, all at once — and bounded identically: a background fetch, a loader that gates on the hero alone, nothing broken, and a next visit that revalidates everything.

A load-time budget on the branch was considered and rejected. This page's TTFB is substantially _server-side_, so a budget would deny `full` to fast-link guests during exactly the event-day database congestion it was meant to protect against — trading a rare, bounded, already-accepted over-pull for a common, unbounded false `lite`. And 9.12 already records that the wall-clock failsafe misresolves a fast-link `pending` guest behind a loaded server to `lite` with no measurement at all: under slow TTFB the locality branch is more right than the failsafe, not less.

The asymmetry decided it: `lite`-on-warm-cache was **certain and common** (every repeat iOS guest, every visit after the first), while the soundtrack over-pull is **rare, bounded, and self-limiting**.

**Load-bearing coupling.** This inference depends on `public/` being served `max-age=0` + ETag, so a returning guest revalidates ~23 assets and each entry reports `transferSize ≈ 300` with `encodedBodySize: 0` — measured on Chromium in this repo, and reported byte-identical on WebKit by an external verification run (local `max-age=0` + ETag server under Playwright WebKit) that was **not independently reproduced here**. The suite now carries a WebKit Playwright project (tasks 7.5/7.10) and the warm-cache `pending` test passes on it — but that gate is outcome-level only, because dev-mode reloads re-download the burst payload instead of revalidating, so the 304 shape itself stays pinned by the node harness (`scripts/tier-verdict-harness.mjs`, task 7.11) rather than observed on WebKit. Treat the WebKit half as confirmatory rather than established. If WebKit in fact reports `0/0/0` for a same-origin 304, the locality branch never fires and a warm-cache Safari guest stays on the failsafe's `lite` — the pre-Option-A behavior, so the rule fails closed rather than wrong. If anyone later "optimizes" `public/` to `immutable` (the files are content-stable, so it looks like a free win), those entries become `transferSize: 0` / `encodedBodySize: 0`, indistinguishable from blocked resource timing, and the warm-cache verdict silently stops firing with no test failing — every repeat iOS guest returns to `lite`. The 304s are the signal, not an inefficiency. `readBurst` carries the same warning at the point of use, and task 7.10 pins it.

**D3 — One-way downgrades.** `full`/`pending` may become `lite`; nothing ever moves back to `full` mid-pageview. An upgrade would collapse-and-repin layouts under a guest who is already scrolling and start megabyte fetches they did not ask for. The visible flip window for `pending → full` is _normally_ hidden behind the loader's 2.6 s minimum dwell, because the burst measurement resolves within it — but that is a tendency, not an invariant, and nothing enforces it. The warm-cache rule in D2 resolves at window `load`, which a stalled subresource or a slow document can push past the dwell and even past gate commit. Consumers are idempotent on every such ordering, so the residual harm is the layout jump described above; see tasks 9.12.

**D4 — Promotion timing per tier; collapse CSS keyed on explicit lite/pending.** Collage images ship as `data-src`/`data-srcset` with intrinsic dimensions. `full`: an inline promoter runs immediately after the collage markup parses and copies sources live — fetch start lands within milliseconds of parse-time. `pending`: promote on resolution to `full`. `lite`: per-image IntersectionObserver promotion with a generous margin, so a lite guest pays only for photos they approach. The pin-collapse CSS keys on `html[data-tier="lite"], html[data-tier="pending"]` (not on `:not([data-tier="full"])`) so a rolled-back build without the head script degrades to today's full behavior rather than a broken static page — which requires the JavaScript consumers to read the attribute the same way, treating an _absent_ `data-tier` as `full`; asking `=== "full"` instead inverts the promise and leaves a 400lvh pinned runway that nothing scrubs and nothing promotes. Alternatives rejected: real `src` for everyone with cancel-on-downgrade (in-flight `<img>` cancellation is unreliable across engines), and `<noscript>` picture duplication for no-JS (~2 KB of duplicate markup per pageview for a tail case). No-JS guests do regress against the immediately preceding state, where `loader-timeline-photo-gate` had given the collage real sources: with nothing to promote the deferred attributes, they see empty frames. A `<noscript>` collapse of the runway to one viewport bounds that to a single screen instead of four; duplicating the `<picture>` markup to actually fill the frames was not worth 2 KB per pageview.

**D5 — Lite scope: skip spend, keep story.** Lite collapses the collage pin, skips the parallax binding, defers collage bytes to approach, removes the video's parse-time fetch (controls, tap-to-play), and skips the soundtrack entirely. The timeline scrub story stays: it is content, its photos are tens of KB each, and its `motion` import keeps the shared animation chunk in the graph regardless — so code-splitting ZoomParallax's import would save nothing and add async-init races. The soundtrack gets no gesture arm on lite: the armed events include `touchend`, so "first gesture" would mean "first scroll swipe silently starts a 3.1 MB download" — precisely the unchosen spend this change removes. The gate's music note hides on lite so the page never promises what it will not deliver.

**D6 — Loader gate shrinks to first-view; ceilings return home.** The loader waits on hero fetch + decode only, raced against an 8 s ceiling (the 16 s value existed solely to give the collage gate runway). The gate CSS failsafe returns to 15 s (it only needs margin over the 8 s ceiling plus commit choreography). Below-fold readiness is now the tiering system's job, not the loader's.

**D7 — Parallax binding stays progress-callback driven.** The scroll binding uses `scroll((progress) => …)` writing transforms directly, per the fix landed earlier this session: passing an `animate()` timeline to `scroll()` never updates on the JS fallback path (object-identity comparison of the fallback timeline's `currentTime`), which is why the effect appeared frozen. Tiering reuses the callback form and simply does not attach it on lite.

## Risks / Trade-offs

- [effectiveType lies in both directions (congested hotspot reports 4g; fast wifi reports 3g)] → D2 measurement downgrades the false `full`; a false `lite` on fast wifi stays lite for the pageview — degraded but complete experience, no broken states.
- [`PerformanceObserver` resource buffering unsupported or blocked] → try/catch keeps the synchronous verdict; `pending` then resolves via the 7 s failsafe to lite.
- [Transfer sizes zeroed for opaque/cached entries shrink the probe below the floor] → transferSize-only accounting is deliberate; the load fallback and failsafe cover thin bursts.
- [Lite guests perceive a missing soundtrack or a static collage as a bug] → gate note hidden on lite; static grid is the same composition the reduced-motion path already ships, so it is a designed presentation, not a broken one.
- [Promotion race: `pending → full` resolving after a lite guest already scrolled past the margin] → promotion margin is generous (well before visibility) and promotion is idempotent; images simply load late rather than never.
- [Two open changes touch welcome-gate behavior] → this change's delta supersedes the below-fold gate half of `loader-timeline-photo-gate`; that change's records carry a pointer note at archive time.

## Migration Plan

Client-only; no data or API migration. Rollout is a normal deploy. Rollback: reverting the commit removes the head script and the attribute consumers; because collapse CSS keys on explicit `lite`/`pending` values (D4), a page without the script behaves as today's full experience.

## Open Questions

None blocking. Threshold (220 KB/s), burst floor (48 KB), and failsafe (7 s) are the tuning knobs to revisit after field observation.
