# Invitation and database contract

Current implementation summary. Detailed requirements are in `openspec/specs/`; coordinated cleanup decisions are in `openspec/changes/guest-photo-clean-baseline/`.

## Invitations

- Share URL: `GET /<id>`, where the ID is a cryptographically random 12-character URL-safe string (`A-Z`, `a-z`, `0-9`, `-`, `_`). The route is `apps/web/src/pages/[id].ts`, not `/i/:id`.
- A known invite increments `seen_count`, sets `seen_at`, binds **or rebinds** `ww_invite_id` to that invite, and redirects to `/`. Existing/stale cookies must not mask a newly opened invitation. **One exception (group invites):** when the link is a _group_ and the incoming cookie already maps to a member **of that same group**, the cookie is re-set to the _same member id_ with a fresh `Max-Age` — sticky identity, sliding expiry — so re-tapping a shared link can never demote a claimed member back to the anonymous group identity. `GET /<groupId>?fresh=1` skips that rule and rebinds to the group id: the explicit release path for shared browsers. Because it is a state-changing GET it is exempt from the framework origin check (safe methods) and `SameSite=Lax` still sends the cookie cross-site, so it is honoured only when `Sec-Fetch-Site` is `same-origin`/`none` and `Sec-Fetch-Dest` is `document` (absent headers allowed through); a refused release still redirects normally and falls back to the sticky rule. The release is **also refused when the group has no open slot** (or its quota cannot be read), so the server agrees with the UI's withheld control instead of honouring a hand-built or history-replayed URL; this gate fails closed. It creates no rows and consumes no slot — only the group row's seen-metrics move, as for any link visit — and leaves the released member's row, RSVP, and photo intact, but it is one-way for that browser (the member id lives only in the cookie, so a re-claim from it mints a new member and consumes another slot). `fresh` has no effect on non-group links. Seen-metrics always bump on the link id, whatever the cookie holds.
- Invalid/unknown links redirect without creating a record or setting an unverified cookie. Tracking is best-effort; database failures must not break the homepage.
- Cookie: client-readable, `Path=/`, `SameSite=Lax`, `Secure` in production, default lifetime 30 days (`INVITE_COOKIE_DAYS`). Possession of a valid invitation identifies the upload/RSVP owner; it is not proof of real-world identity.
- `POST /api/invite/opened` updates `opened_at`/`opened_count`. Homepage rendering and `GET /api/invite/me` are read-only — for group and member cookies too, and on every repeated call.
- `GET /api/invite/me` returns `{ displayName, kind }`, where `kind` is `"individual"`, `"member"`, or `"group"`, plus `group: { maxMembers, claimedCount }` for group cookies only. Individual and member responses carry no `group` field, and no other fields are returned.
- Missing, malformed, and unknown cookies receive the same empty `404` from private APIs. Infrastructure errors are `503`, not identity misses. One deliberate exception: `POST /api/invite/opened` validates cookie _shape_ and then lets its single-statement metrics `UPDATE … RETURNING` discover whether the row exists, so a syntactically valid but unknown cookie combined with a cross-origin `Origin` gets `403` rather than `404`. Not browser-reachable (`SameSite=Lax` withholds the cookie on cross-site POSTs) and it discloses nothing about whether the id exists, since the `403` precedes the read; the other three endpoints DB-resolve first and `404` before their guards. Public photo collection reads instead serve anonymous posting state.
- Personalized HTML, identity APIs, redirects, RSVP responses, and photo collection/upload responses use `Cache-Control: no-store`.

## Group invitations

One shareable link can serve a family or a party. Group state lives in the same `invites` table:

- **Group invite** — `type = 'group'` with a non-null `max_members`. **Member invite** — `type = 'individual'` with a non-null `parent_id`. **Standalone individual** — `type = 'individual'`, `parent_id IS NULL`. "Member" is never a stored `type` value: a member is an ordinary individual row, so the RSVP, photo, greeting, and open-tracking contracts apply to it unchanged.
- Opening `/{groupId}` is free and unlimited — it bumps the group row's seen-metrics and sets the group cookie, nothing more. **Only an explicit claim consumes a slot**, so forwarding the link, a chat preview, or an accidental tap costs nothing.
- `POST /api/invite/claim` resolves identity from the cookie BEFORE reading the body, mints one member row, and rebinds `ww_invite_id` to it using the identical cookie attribute set. Body `{ "displayName": string }`, trimmed, 1–120 characters. A first claim returns `201 { displayName, kind: "member" }` with no invite id in the body; an already-claimed member gets an idempotent `200` and its body is never read. Missing, malformed, and unknown cookies get the same bare `404` as every other private API; a standalone individual cookie gets `409 { "error": "not_a_group" }`; a cross-origin `Origin` header gets `403 { "error": "cross_origin_post" }`, compared proxy-aware so a TLS-terminating reverse proxy does not make every legitimate claim look cross-origin. A claim writes no metrics.
- The quota is enforced by **one atomic statement** — `INSERT … SELECT … WHERE member_count < max_members … RETURNING` in `apps/web/src/lib/group-claim.ts`. SQLite serializes writes, so concurrent claims cannot over-allocate: the loser's statement inserts zero rows and the caller gets `409 { "error": "group_full" }`. `group_full` is reserved for a successfully executed statement that inserted nothing while the group still exists; a vanished group, an unknown re-check, or any storage failure (including `SQLITE_BUSY`) is a retryable `503`, never a false "full". It must never degrade into read-then-write, and no other code path may insert rows with `parent_id` set.
- A full group stays browsable: the link, cookie, greeting, photos wall, and public RSVP count all keep working. Only slot-consuming actions are blocked, and client surfaces present a read-only "group is at capacity" state.
- Members are fully independent — own `display_name`, metrics, RSVP row, and photo slot. The group row itself never holds an `rsvps` or `guest_photos` row, and the public count adds one per attending member.
- Identity kind reaches the RSVP surface server-side (`index.astro`'s own inline query) and the photo surface client-side (`GET /api/invite/me`). Both share ONE claim affordance, and a successful claim does a full page reload so every server-rendered surface re-renders under one consistent member identity. The "Not you? Claim your own spot" release control sits behind a two-step confirmation with a minimum interval between the two activations, because the release is one-way for that browser. It is a `<button>` carrying its target in `data-release-href`, never an anchor: a static `href` is reachable by middle-click, the context menu, iOS long-press, drag-to-bookmarks, copy-link and a no-script tap, all of which bypass the two-step and reach the destructive endpoint with gate-passing `Sec-Fetch` metadata. It renders only while the parent group has an open slot — at capacity a release could only strand the member.
- Cookie identity means one person can claim several slots from several browsers. The quota bounds the blast radius and the admin breakdown makes duplicates visible; there is no slot-level unclaim.

### 409 taxonomy, by endpoint

Clients MUST branch on the JSON `error` code, never on the `409` status alone.

| Endpoint                 | Possible `409` codes               |
| ------------------------ | ---------------------------------- |
| `POST /api/invite/claim` | `not_a_group`, `group_full`        |
| `POST /api/rsvp`         | `claim_required`                   |
| `POST /api/guest-photos` | `already_posted`, `claim_required` |

`group_full` is never an RSVP or photo outcome, and `claim_required` is never a claim outcome. An unreadable or unrecognized `409` body is an uncertain outcome: the photo client refreshes and never marks the upload committed. Group-cookie READS stay valid and unguarded — `GET /api/rsvp` returns `200 { "attending": null }` and `GET /api/guest-photos` returns `200 { "inviteValid": true, "mineId": null }`.

## Origin checks on mutating endpoints

`security.checkOrigin` is **disabled** in `astro.config.mjs`, deliberately. Astro compares `Origin` against `new URL(request.url).origin`, and `request.url`'s scheme comes from `req.socket.encrypted` — false behind the documented Caddy deployment, where TLS terminates upstream. Every form-like and bodiless POST therefore 403'd in production (guest photo upload and invite-open tracking were dead; `/api/rsvp` survived only because JSON bodies are exempt). It cannot be fixed from config: the same predicate is applied in `core/middleware/load.js` (which `unshift`s the check ahead of user middleware) and again in `core/pages/handler.js` via `core/fetch`, both before a route handler can act; `site:` never reaches `new URL(request.url)`; and `security.allowedDomains` only feeds a validator the node adapter calls with `void 0` for the protocol. One exposure is genuinely new and currently vacuous — `checkOrigin` also guards Astro Actions, of which this project has none; a future Action would be served at `/_actions/*` with no origin check and would be invisible to `tests/origin-guard.spec.ts`, so extend that test's inventory before adopting them.

It is replaced by `isSameOriginRequest()` in `apps/web/src/lib/same-origin.ts`, which reconstructs the public origin from `X-Forwarded-Proto`/`X-Forwarded-Host`. Every cookie-authenticated POST calls it and answers a cross-origin request with `403 { "error": "cross_origin_post" }`; a request with no `Origin` header is allowed, so non-browser callers keep working. `POST /api/admin/{token}/invites` is exempt: its authority is a secret in the path, not an ambient cookie, so CSRF cannot supply it. `tests/origin-guard.spec.ts` fails if an endpoint drops the call, if `checkOrigin` is re-enabled, or if a cross-origin POST changes any state (which is what pins the guard to run _before_ its side effect, not merely to exist somewhere in the handler).

## Admin

`GET` and `POST /api/admin/:token/invites` require `INVITE_ADMIN_TOKEN` (at least 32 characters). Wrong/unconfigured tokens return `404`. Do not expose the path token in logs or public links; call it only over HTTPS in production.

POST accepts a trimmed nonempty `displayName` (at most 120 characters), an optional `type` (`"individual"`, the default, or `"group"`), and an optional `maxMembers`. A group requires an integer `maxMembers` of 2–50; an individual must not carry one. Responses are `201 { id, sharePath: "/<id>", type: "individual" }` and `201 { id, sharePath: "/<id>", type: "group", maxMembers }`. Validation failures return `400` with a specific code — `invalid_json`, `display_name_required`, `display_name_too_long`, `invalid_type`, `invalid_max_members`, `invalid_parent_id`. **Member rows cannot be created here:** any non-null `parentId` is rejected (an explicit `null` is equivalent to omitting it), because the atomic claim statement is the only writer allowed to consume a slot. Id-collision retries use a precise classifier, so a CHECK or FK failure surfaces as `500 invite_create_failed` immediately instead of burning retries.

GET reports invitation tracking and RSVP attendance. Every row — standalone individuals, groups, and members — is a top-level entry carrying `type`, with `parentId` on members; individuals otherwise keep their flat shape. Group entries add `maxMembers`, `claimedCount`, `attendingCount`, `declinedCount`, `photoCount`, and a `members[]` breakdown of `{ id, displayName, attending, openedAt, openedCount, hasPhoto }`, ordered newest-claimant-first (the list is `createdAt DESC, id DESC`). Member `seen_*` is deliberately omitted: link metrics bump on the link id, so member seen-counters are normally zero and reporting them would only invite a wrong reading. The list costs one query over `invites`/`rsvps`/`guest_photos` plus in-JS grouping — no per-member queries.

## Current tables

- `invites`: `id`, `display_name`, `created_at`, nullable `seen_at`/`opened_at`, zero-default `seen_count`/`opened_count`, nullable self-referencing `parent_id`, `type` (NOT NULL, default `'individual'`), and nullable `max_members`; indexed on `parent_id`. Four CHECKs pin the row shapes: `invites_type_chk` (`type` ∈ `individual`,`group`), `invites_group_shape_chk` (`type='group'` ⟺ `max_members IS NOT NULL`), `invites_member_shape_chk` (`parent_id` ⇒ `type='individual'`), `invites_max_members_range_chk` (`max_members` between 2 and 50). There is no stored member count — it is always `COUNT(*) WHERE parent_id = ?`, so it cannot drift.
- `rsvps`: primary-key/FK `invite_id`, boolean `attending`, first `responded_at`, latest `updated_at`; index on attendance. Upserts preserve the first response timestamp. Public count means attending invitations, not party headcount.
- `guest_photos`: `id`, unique FK `invite_id`, unique canonical `key`, `created_at`; index `(created_at, id)`. One accepted photo per invitation. No parent submission, ordering position, wish, party-size, thumbnail, or copied author fields.

The application enables SQLite foreign keys. Dependencies use no-action deletion: operators must not delete invitation rows underneath RSVP/photo records. The `invites.parent_id` self-FK is a mechanical backstop on that rule — deleting a group that still has member rows fails, while a memberless group can be deleted.

## Guest photos

`GET /api/guest-photos` returns `{ inviteValid, mineId, photos: [{ id, photoUrl, createdAt }] }`. It includes all photos once in descending timestamp/ID order, with no public invitation IDs or names. A group cookie reads exactly as any invite with no photo: `inviteValid: true`, `mineId: null`. Each group member holds their own single slot through the same unique `invite_id` constraint.

`POST /api/guest-photos` resolves the cookie before body parsing and accepts exactly one multipart file named `photo`, at most 10 MiB. JPEG/PNG/WebP/AVIF are validated by content and decoder. Every canonical is safe WebP, orientation-corrected, dimension-capped and metadata-free; optional AVIF is generated afterwards. Files are complete before the row is published. Duplicate invitation ownership returns `409 already_posted`, and an unclaimed group cookie returns `409 claim_required` after the origin guard but before any body or storage handling — those are the only two `409` outcomes of this endpoint, and clients must branch on the code, never the status. Other failures cannot delete another upload's files.

Stored paths are `guest-photos/<photo-id>/photo.webp` and optional `photo.avif`, served publicly by `/api/photos/<key>` with immutable caching and `Vary: Accept`. The magnetic trail uses family starter images only as presentation fallbacks; they are not database records.

## Migration and operations

Generate changes with `pnpm run db:generate`; apply committed history with `pnpm run db:migrate`. `db:push` is not a release command.

The current initial migration is fresh-install-only. Existing legacy environments require an explicitly authorized replacement or a data-preserving migration plan, never an automatic reset. See `README.md` and `ops/README.md` for explicit targets, matched rollback, and backup verification. No IP addresses, user agents, or referrers are stored for invitation tracking.
